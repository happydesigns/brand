The happydesigns layer should give every standard Nuxt UI component used by this project a clear role in the brand system, either through a focused example or through a larger integrated pattern. This guide does not repeat the full Nuxt UI documentation and does not re-verify Nuxt UI's own behavior.

`Documented` means that the component or family is demonstrated with happydesigns guidance. `Verified` is reserved for behavior changed by `brand` or `id` that has an automated integration check or an explicit accessibility review. Inherited Nuxt UI behavior does not need a duplicate test here.

## Review priority

1. Form controls and validation states.
2. Feedback states, especially warning and error behavior.
3. Tables and dense data surfaces.
4. Overlays and destructive flows.
5. Layout, docs, and prose surfaces.
6. Navigation components across docs and product contexts.
7. Product-specific groups: dashboard, publishing, chat, editor, pricing.

## Theme checklist

- Shared visual behavior is derived in `app/utils/brand-theme.ts` and wired through `app/app.config.ts`.
- Neutral palette values originate in `app/utils/brand-data.json` and generate `app/assets/css/brand.generated.css`.
- `app/assets/css/main.css` consumes theme variables for global composition and brand-only utilities.
- Docs examples use real Nuxt UI components.
- Page-specific classes are limited to layout, spacing, and demo composition.
- New components are assigned to a family before they get one-off styling.
